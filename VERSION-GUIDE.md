# chdb-core version and release tags

chdb-core's version is distinct from the higher-level [chDB DataStore package](https://github.com/chdb-io/chdb). A chdb-core release tag has one of two forms:

- `vX.Y.Z` for a release (for example, `v26.11.1`).
- `vX.Y.Z-rc.N` for a release candidate (for example, `v26.11.0-rc.3`).

`X.Y` is the ClickHouse baseline line recorded in
`cmake/autogenerated_versions.txt`. It must match the tree being released.
`Z` counts chdb-core kernel changes on that line; it is **not** ClickHouse's
upstream patch or revision number. A candidate that includes another kernel
change may advance `Z` as well as its `rc.N` suffix. Both `Y` and `Z` must be
below 100 for downstream binding version encodings. See
`.github/scripts/check-release-tag.sh` for the enforced tag format and line
check.

`UPSTREAM_COMMIT` records the exact ClickHouse `main` commit last synced into
this tree. At this release preparation it is
`e497200754be91200b5fe274a701786221d3d2af`. The generated version file
still says `26.11.1.1-testing`; its revision and hash can lag later master
syncs, so do not present that string as the exact upstream release or commit.

For the current 26.11 line, `v26.11.0-rc.1`, `v26.11.0-rc.2` and
`v26.11.0-rc.3` are existing candidates. The final release is `v26.11.1`.
Its download assets become available after the published-release build jobs
finish. Release candidates do not go to PyPI; a final release may opt out of
PyPI with `[no-pypi]` in its GitHub release notes.

The source defaults in `pyproject.toml`, `chdb/__init__.py`, `docs/conf.py`,
`.bumpversion.toml` and `programs/local/chdb.h` describe the release being
prepared. Release jobs stamp the Python package version and the public C
header from the tag they build, while non-release wheel jobs generate a
development version. Before tagging, run:

```bash
.github/scripts/check-release-tag.sh v26.11.1
.github/scripts/check-abi-version.sh
```

The tag and GitHub release are separate remote publishing actions. Check the
release's target commit, notes, CI and intended PyPI policy before creating
either one.
