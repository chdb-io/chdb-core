## 1. Two decisions that need your call

Everything in §2 has a recommendation I am confident in. These two do not.

### D1 — Upstream deleted the Apache-Arrow-library Arrow reader/writer, which is the path chdb forces on

Upstream commit `559f3d411d77` *"Remove the Apache Arrow library reader and writer for the Arrow
formats"* deletes `ArrowBlockInputFormat.{cpp,h}` and `ArrowBlockOutputFormat.{cpp,h}` and replaces
them with a hand-written `src/Processors/Formats/Impl/ArrowIPC/` subsystem. The registration entry
points are unchanged (`registerInputFormatArrow` / `registerOutputFormatArrow`), so the deletion
compiles — which is exactly the problem.

Evidence:

* chdb **forces the deleted path on**: `programs/local/EmbeddedServer.cpp:257` and
  `programs/local/LocalServer.cpp:308` both set
  `settings[Setting::output_format_arrow_use_native_writer] = false;`
* At v26.9 that setting is **still declared** in `FormatFactorySettings.h` but has **zero consumers**
  in `src/` (`format_settings.arrow.output_use_native_writer` is gone from `FormatFactory.cpp`).
  So the two setter calls keep compiling and silently become no-ops — a Hazard-2 silent behaviour
  change, not a build break.
* chdb carries real work in the deleted files:
  `b897f7ff6b7b feat(arrow): parallel encoding for Arrow / ArrowStream output formats`
  (+265/−24 in the `.cpp`, +58/−1 in the `.h`),
  `ad7105c879b3 Fix deadlock in the parallel Arrow output encoder backpressure wait`,
  `aba30a8d8a53` / `fba3c773d5ce` ADBC compatibility.
* `output_format_arrow_parallel_encoding` is **chdb's own setting** — absent from both upstream tags.
  Its implementation lives entirely in the deleted `ArrowBlockOutputFormat`.
* Upstream's new `ArrowIPCBlockOutputFormat` has **no threading at all** (no `ThreadPool`,
  no `max_threads`) — parallel encoding is not something upstream picked up.
* The only chdb reference to the old classes outside the four files is
  `tests/test_arrow_parallel_encoding.py`.

Options:

* **(a) Keep the four files.** Do not mirror the deletion; keep `output_format_arrow_use_native_writer`
  wired in chdb's own `FormatFactory.cpp` so the setter still selects the Apache path. Cheapest, keeps
  parallel encoding and ADBC behaviour identical. Cost: chdb now carries a subsystem upstream deleted,
  and this conflict returns, larger, at every future sync.
* **(b) Mirror the deletion and port.** Delete the four files, drop the two `= false` setter calls,
  and port parallel encoding + the ADBC compatibility bits onto `ArrowIPC/`. Correct long-term;
  it is a real piece of work and `tests/test_arrow_parallel_encoding.py` is the spec to hold it to.
* **(c) Mirror the deletion, drop parallel encoding for now.** Fastest to green. This *removes a
  shipped feature and its setting* and would silently change ADBC output. I would not do this without
  it being an explicit, recorded product decision.

**My recommendation: (a) for this PR, with (b) filed as a follow-up.** A baseline bump should not be
the commit that rewrites chdb's Arrow output path; bundling them makes both unreviewable and gives
`git bisect` nothing to land on.

19 of the 69 conflicts are the same collision: chdb-core's WASM work

**My recommendation: (a).** §2 group G1 is written assuming (a): 19 files become pure
`--theirs`, which also deletes 19 recurring conflicts from every future sync. The chdb-only WASM
*features* are preserved — they are in group G2 and are not touched by this choice.

If you pick (b) instead, G1 flips to "keep ours" and I redo those 19 entries.

## 9. The minimized static library dropped one object

`chdb/build/build_static_lib.sh` completed on Linux, but the Go cgo test then failed to link:

```
undefined reference to `typeinfo for DB::ASTSQLSecurity'
undefined reference to `vtable for DB::ASTSQLSecurity'
```

The cause is a hand-written exclusion in `chdb/build/create_minimal_libchdb.py`:

```python
# Force exclude any object files containing ASTSQLSecurity
objects_to_extract = {obj for obj in objects_to_extract if 'ASTSQLSecurity' not in obj}
```

Added in `5099e89e1a5c` ("test: test ci", 2025-08-07) with no stated reason. It contradicts
the keep-list it filters: `chdb/build/chdb_objects.txt` is 9170 lines and **does** list
`libclickhouse_parsers__ASTSQLSecurity.cpp.o`, which is why the script's own output reads
`Required object files: 9170` / `Found required object files: 9169`.

Dropping that object was survivable only while nothing in the kept set referenced it. v26.9
added AST JSON serialization, and `src/Parsers/ASTAlterQuery.cpp` now instantiates
`JSONObjectReader::readChildOfType<ASTSQLSecurity>`; at v26.7 that file did not mention
`ASTSQLSecurity` at all. Go cgo links with `--whole-archive`, so the kept set has to be closed
under reference, and from v26.9 it no longer is.

Confirmed before changing anything: `ar x` the object out of `libchdb.a`, `ar q` it onto the
existing `libchdb_minimal.a`, rerun `chdb/build/test_go_example.sh` — every Go example passes.
The exclusion is removed here, and the comment in its place records what it was and why it
cannot come back. The full minimization was then re-run from `libchdb.a` through the fixed
script, so the verified artifact is the one the script produces, not the one patched by hand.

Two steps ran on Python 3.9 rather than CI's 3.11: the wheel built here carries only the 3.9
`libpybind11nonlimitedapi_chdb_*.dylib` shim, because `chdb/build.sh` builds one per pyenv
version present and this machine has only 3.9. Both steps test linking and import order, which
the interpreter version does not change. The numba check also used `--override-channels
-c conda-forge` so it never touches Anaconda's own channels, which now require accepting their
terms interactively.

Three local-environment notes that are not defects:

- `examples/runCppExamples.sh` does not compile: `programs/local/chdb.hpp` declares
  `namespace CHDB` while all four `examples/chdbCpp*.cpp` say `chdb::`. Identical on
  `origin/main`, and no workflow invokes the script, which is how it went unnoticed. Not this
  PR's to fix.

- `chdb/build.sh`'s `CHDB_LITE` branch omits `${JEMALLOC}`, which
  `chdb/build_mac_on_linux.sh:158` passes. A native macOS lite configure therefore aborts,
  because lite forces `Release` and jemalloc allows only `RelWithDebInfo`/`Debug` on Darwin.
  Pre-existing (the gate is byte-identical at both tags) and invisible to CI, which builds
  lite by cross-compiling. Not fixed here; it is not this PR's to fix.
- `examples/runVersionHeaderTest.sh` compares the header's compile-time `CHDB_VERSION`
  against the linked library's. They disagree locally whenever the library was built before
  `chdb/vars.sh` restamped the header. Build with `CHDB_VERSION=<value>` set to keep both in
  step; CI derives one value from the tag and never sees the skew.
