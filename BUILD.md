# BUILD.md — chdb-core build & test guide

This file is the long-form build / test manual for chdb-core. The
short version (what command do I run, what tests do I rerun, what to
do for each kind of change) lives in
[`CONTRIBUTING.md`](./CONTRIBUTING.md) → "Setting up" / "I changed X
— what to run" / "Day-to-day commands". Come here when the short
version isn't enough.

## 1. Prerequisites

- macOS arm64 (M1/M2/M3) or x86_64, or Linux x86_64 / arm64
- **Python 3.9 on `PATH` for building** (`chdb/build.sh` exits
  otherwise — 3.9 is the abi3 / Limited-API anchor). Built wheels
  run on 3.9–3.14; only the build host has to be 3.9. Use
  `pyenv shell 3.9.13` if your default is newer.
- Git 2.30+
- ~60 GB free disk

### Toolchain (C++ compiler, CMake, Ninja, optionally ccache)

The recommended path on macOS is Homebrew:

```bash
brew install llvm@21 cmake ninja ccache
# build.sh picks up llvm@21 from `brew --prefix llvm@21` automatically.
```

The authoritative minimum versions live in the source tree, so they
stay correct across upstream syncs:

- **clang** — [`cmake/tools.cmake`](./cmake/tools.cmake), the
  `CLANG_MINIMUM_VERSION` constant.
- **Rust toolchain** — [`rust/vendor.sh`](./rust/vendor.sh), the
  `TOOLCHAIN` variable (a `rustup` nightly date).

If you don't have Homebrew, `chdb/build.sh` falls back to the system
Apple clang (Xcode Command Line Tools), and you can install CMake +
Ninja into a venv via pip:

```bash
python3 -m venv .build-venv
.build-venv/bin/pip install cmake ninja
export PATH="$PWD/.build-venv/bin:$PATH"   # so make / build.sh find them
```

ccache is optional — without it, the first build is just slower.

### tox

`make build` wraps `tox -e build` for the wheel step and `tox -e
clean` for the clean step, so tox needs to be on `PATH`:

```bash
pip install tox
```

### Linux

The toolchain expectations match ClickHouse upstream — see
ClickHouse's official build documentation for the package list.

## 2. Clone with submodules

```bash
git clone https://github.com/chdb-io/chdb-core
cd chdb-core
git submodule update --init --recursive
# ↑ several GB, 5–15 minutes depending on network
```

For docs-only or read-only browsing on a slow connection, a shallow
clone is much faster (`--depth 1`) — but for a build you do need full
submodule history.

## 3. First build

```bash
make build       # equivalent to: clean buildlib wheel
# OR build only the C++ library:
cd chdb && bash build.sh
```

`make build` produces a wheel under `dist/`. Time budget on a recent
M-series MacBook Pro: 1–3 hours for a from-scratch build. With a
primed ccache, incremental rebuilds are 1–10 minutes for typical C++
edits.

The wheel filename uses the Python-package version from
`pyproject.toml` (currently `0.0.1b1` in local builds — it gets
overridden to the git-tag version only in release CI), not the
ClickHouse engine version. The engine version lives separately in
`cmake/autogenerated_versions.txt` and surfaces in `SELECT version()`.

## 4. Install the freshly built wheel

Two options — pick one:

```bash
# (a) Clean wheel install — matches what end users get:
pip install dist/chdb_core-*.whl --force-reinstall

# (b) Editable install — faster iteration; uses the source tree
#     instead of the wheel artefact:
pip install -e .
```

`import chdb` works after either install. Sanity check:

```bash
cd /tmp && python -c "import chdb; print(chdb.query('SELECT 1+1'))"
```

> **Note**: The `cd /tmp` applies *only* to this sanity-check
> command, not to `pip install` above. Inside the chdb-core repo,
> the local `chdb/` subdirectory shadows the installed wheel and
> `import chdb` fails with
> `ImportError: cannot import name '_chdb'` (unless the C extension
> was just built locally), so the import test has to run from
> elsewhere.

## 5. Verify a chdb-core change end-to-end from the chdb repo

The wheel you just built carries the engine-side change, but real
end-to-end coverage lives in
[chdb-io/chdb](https://github.com/chdb-io/chdb) (DataStore + the
broader Python test suite). After a successful `make build`, point
chdb at your local wheel:

```bash
# From a checkout of chdb-io/chdb, in the same Python env:
pip install /path/to/chdb-core/dist/chdb_core-*.whl --force-reinstall
pip install -e .                            # if not already
cd datastore && python -m pytest tests/ -v --tb=short -x
```

You may see `pip` warn that `chdb x.y.z requires chdb-core>=26.1.0,
but you have chdb-core 0.0.1b1` — that's expected, because the
locally-built wheel uses the `pyproject.toml` placeholder version
rather than a release tag. `--force-reinstall` overrides the version
pin, and `import chdb` works regardless.

To confirm your engine change is loaded:

```bash
cd /tmp && python -c "import chdb; print(chdb.query('SELECT version()'))"
# Should print the VERSION_STRING you set in
# cmake/autogenerated_versions.txt
```

If the chdb suite goes green and `SELECT version()` returns the
expected string, the engine change is good for a PR there. If chdb
fails, the breakage is visible to users — fix it before merging.

## 6. Build & test commands (paste-able)

### 6.1 Full build (release wheel)

```bash
make build              # = clean buildlib wheel
# Output: dist/chdb_core-*.whl
```

### 6.2 Library-only build (faster iteration)

```bash
cd chdb && bash build.sh
# Default build_type is Release; pass Debug as $1 for a debug build:
cd chdb && bash build.sh Debug
```

### 6.3 Platform-specific scripts

```bash
chdb/build_mac_on_linux.sh     # cross-build macOS from Linux (used by macos_*_wheels.yml)
chdb/build_pybind11.sh         # pybind11 non-limited-API layer (invoked from build.sh)
```

### 6.4 Run tests

```bash
make test                                          # = cd tests && python3 run_all.py
cd tests && python3 -m pytest test_<file>.py -v    # targeted, while iterating
```

### 6.5 Lint (Python only)

The Python lint configuration is `[flake8]` in `setup.cfg`, scoped to
critical errors only:

```bash
flake8 chdb --count --show-source --statistics
```

### 6.6 Hygiene

```bash
make clean           # removes buildlib/, dist/, *.egg-info via tox -e clean
# Aggressive (free disk after a stuck build):
rm -rf buildlib/ dist/ *.egg-info build/
# Reset ccache (only if convinced it is corrupted):
ccache -C
```

> ⚠️ `make clean` also `rmtree`s tracked files under `chdb/build/`
> — see [`CONTRIBUTING.md`](./CONTRIBUTING.md) → "Prefer the
> smallest-scope rebuild over `make clean && make`" for details and the
> `git checkout HEAD -- chdb/build/` restore command.

### 6.7 Re-pin a single submodule

```bash
# Coordinate before doing this — see CONTRIBUTING.md "Coordinate ClickHouse / contrib submodule bumps via an issue" and UPSTREAM_SYNC.md
cd contrib/<lib-name>
git checkout <new-pin>
cd ../..
git add contrib/<lib-name>
# Open an issue describing why before committing.
```
